# ADR 0009: Reconciliation by chunked keyset scan, validated against planted errors

**Status:** Accepted
**Date:** 2026-09-20

## Context

With transactions in the event log and a calculator that knows the rules, the
product's actual function is to compare the two across a whole batch.

Two questions had to be answered: how to walk a million rows, and how to know
the answer is right.

## Decision: walk the batch in keyset-paginated chunks

Three options were considered.

**Load the batch into a list.** The same mistake as `readAllLines`: a million
rows held at once costs hundreds of megabytes, and the cost grows with the
customer.

**One streaming cursor.** Works, but holds a single database transaction open
for the whole run. Long transactions block vacuum, accumulate WAL, and make the
run an all-or-nothing unit that cannot resume.

**Chunked keyset pagination.** Chosen. 5,000 rows per page, each page a short
statement, with breaks written per page.

Crucially the paging is by **keyset**, not OFFSET:

```
OFFSET 500000 LIMIT 5000   -- database reads 505,000 rows and discards 500,000
WHERE id > ? LIMIT 5000    -- index seeks straight to the position
```

OFFSET pagination degrades with every page because the database must count past
everything it has already returned; over a million rows that is quadratic. A
keyset remembers where it stopped, so page 200 costs what page 1 cost. The index
on `transaction_event` was widened to `(batch_id, id)` to support it.

Re-running is made idempotent the same way ingestion was: a unique index on
`recon_break.transaction_event_id` plus `ON CONFLICT DO NOTHING`. Re-running
after a restatement, a rules change, or a double click cannot duplicate
findings.

Transactions whose rule is unspecified (education, credit-linked) are counted
and skipped, never broken. With no published rate there is no defensible
expectation, so asserting a break would mean disputing a charge under a rule we
admit we do not know.

## Decision: classification precedence

`CHARGED_WHEN_EXEMPT` and `CAP_BREACHED` are checked before `OVERCHARGED`,
because the categories overlap and the more specific one makes the stronger
claim. "You charged an exempt merchant" and "you exceeded the regulator's cap"
each cite a specific rule. "You charged slightly too much" invites an argument
about rounding. As in the calculator, precedence is contract, not detail.

## Validation: plant known errors, then count what is found

A detection engine cannot be validated against data whose correct answer is
unknown -- every output looks equally plausible. So the test file is generated
with a **known number of deliberately corrupted rows**, and the run must find
exactly those.

The generator computes correct MDR with an **independent second implementation**
in Python rather than calling the Java code. Generating the expectations from
the implementation under test proves only that the code agrees with itself.

Result over 1,000,000 rows:

| break type | planted | found |
|---|---|---|
| CHARGED_WHEN_EXEMPT | 1,500 | 1,500 |
| CAP_BREACHED | 800 | 800 |
| OVERCHARGED | 3,000 | 3,000 |
| UNDERCHARGED | 2,000 | 2,000 |
| **total** | **7,300** | **7,300** |

Scan time: 3.0 seconds. Recoverable: Rs 133,846.

## What cross-validation caught

The first run found 15,474 breaks against 7,300 planted -- 8,174 too many, every
one of them a capital-markets row off by **exactly one paise**.

The two implementations disagreed on rounding: the generator truncated
(66.66 -> 66) where the calculator rounds HALF_UP (66.66 -> 67). The Java was
correct, matching the documented decision in `MdrCalculator.ROUNDING`; the
generator was wrong.

This is precisely the failure predicted in open question 5: *"systematic
rounding differences will surface as false breaks."* One paise of disagreement
produced 8,174 false claims. Had those been filed, every one would have been
wrong, and the product's entire premise -- that our arithmetic is right --
would have been destroyed on first contact with a customer.

It also demonstrates why the second implementation had to be independent. Had
the expectations been generated by calling `MdrCalculator`, the test would have
passed perfectly and proved nothing.

The open question is unchanged and now has evidence attached: until the NPCI
circular states the rounding rule, this class of false break is a live risk
against any real PSP whose rounding differs from ours.

## Consequences

- Memory is independent of batch size; 1,000,000 rows scan in a 256 MB heap.
- Reconciliation is repeatable without duplicating findings.
- The run is **synchronous**, repeating D2. At 3 seconds it is tolerable, but it
  scales with the batch and should move to the pattern in ADR 0008. Recorded as
  D6.
- Only breaks get a `mdr_calculation` row. The calculation is pure and
  deterministic given its input and ruleset version, so storing a million
  derivable rows would trade storage for nothing.
