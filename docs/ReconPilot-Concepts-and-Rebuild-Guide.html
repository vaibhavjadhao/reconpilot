1 · The machine

Before any code, the tools. Each one exists because a specific job would otherwise be done by hand, badly, repeatedly.

1.1 Homebrew — a package manager for your operating system

Analogy

When you want WhatsApp on your phone, you don't visit their website, work out which build matches your chip, download an installer and tell the phone where it went. You open the Play Store and tap install. The store finds it, fetches the right version, installs it, and updates it later.

macOS has no such store for developer tools. Homebrew is the one the community built.

Installing Java without Homebrew means: pick a vendor (Oracle? Adoptium? Amazon? Azul?), pick a build (ARM64 or x86? JDK or JRE? 17, 21 or 25?), download a .dmg, run an installer, set JAVA_HOME by hand, add it to PATH by hand — and repeat all of it to upgrade or to run two versions side by side.

With Homebrew: brew install openjdk@21.

The pattern to notice

Homebrew is a dependency manager — the same idea as Maven for Java or npm for Node, operating one layer down at the level of your operating system. You declare what you want; it works out what that needs, fetches everything, and records it so it can be removed cleanly.

"Declare intent, let the tool resolve the graph." You will meet this idea four more times in this document: in Maven, in Docker, in Docker Compose, and in Spring's dependency injection. Recognising a pattern across technologies is most of what makes an experienced engineer fast in an unfamiliar stack.

1.2 The JDK, and why version choice is an engineering decision

Java ships a new version every six months, in March and September. Most are feature releases, supported for about six months. Roughly every two years one is designated LTS — Long Term Support — and receives security patches for years.

LTS line:   8  →  11  →  17  →  21  →  25

Enterprises run LTS versions, almost without exception. No bank runs Java 27 in production.

We chose 21. You are learning Java to be hired, so you want fluency in what companies actually run. Java 21 is also where virtual threads landed, which is the hottest Java interview topic right now. Nothing is lost: everything you learn on 21 works identically on 25.

OpenJDK vs "distributions" — the thing that confuses everyone

OpenJDK is the source code — the free, open-source reference implementation. Nobody downloads "OpenJDK the product"; you download someone's build of it: Eclipse Temurin, Amazon Corretto, Azul Zulu, Microsoft's build, Oracle JDK.

Analogy

OpenJDK is the recipe. Temurin, Corretto and Zulu are different bakeries using it. The bread is essentially identical — all are TCK-certified, meaning they pass Oracle's official compatibility suite. They differ in support contracts, release cadence and minor tuning.

This matters practically: Oracle's own JDK has had licensing terms that made companies nervous about production use, which is precisely why Temurin and Corretto exist. If asked "which JDK and why?", answering "Temurin, because it is TCK-certified and free of Oracle's commercial licensing constraints" is a strong answer for a two-year developer.

JAVA_HOME — what it is and why builds break without it

An environment variable is a note pinned to your shell that every program can read. JAVA_HOME is the note saying "the JDK lives at this exact path." Maven, Gradle, IntelliJ, Tomcat and nearly every Java tool read it rather than guessing.

# in ~/.zprofile
export JAVA_HOME="/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"
This bit us twice

~/.zprofile is read only by zsh login shells. IntelliJ launches Maven through /bin/sh, so JAVA_HOME never reached it and it fell back to JDK 27 — where Lombok's annotation processor crashed with ExceptionInInitializerError: com.sun.tools.javac.tree.EndPosTable.

Configuration that lives in a shell profile is invisible to anything that is not that shell. Not /bin/sh, not an app launched from the Dock, not a CI runner, not a Docker container. A build that only works because of your shell is not reproducible — which is exactly what CI exists to catch.

1.3 Maven — dependencies plus a standard build

You already know this concept from two directions: package.json and npm in Angular, NuGet and MSBuild in .NET. Maven is both, plus strong opinions about your folder layout.

Three jobs

1. Dependency management. You write in pom.xml: "I need Spring Boot Web." Maven downloads it — and everything it needs, and everything those need, recursively. That recursion is called transitive dependencies and is the whole reason these tools exist. Spring Boot Web pulls in around thirty libraries you never asked for and shouldn't have to think about.

We watched this happen live

brew install maven printed:

==> Installing maven dependency: openjdk
🍺  /opt/homebrew/Cellar/openjdk/27: 535 files, 391.2MB

Maven dragged Java 27 in as its own dependency. Suddenly there were four JDKs on the machine — and JAVA_HOME is what decided which one Maven actually used.

2. A standard build lifecycle.

validate → compile → test → package → verify → install → deploy

mvn package runs every phase up to and including package. The point is that every Maven project on earth builds the same way — you can clone a project you have never seen and know that mvn package will build it.

3. Convention over configuration. Maven doesn't ask where your source is. It knows:

src/main/java        your code
src/main/resources   config files
src/test/java        your tests
target/              build output
Burn this phrase into memory

"Convention over configuration" means the tool assumes sensible defaults so you only configure the exceptions. Spring Boot is built entirely on this philosophy. When an interviewer asks "why is Spring Boot better than plain Spring?", this idea is the answer.

The Maven wrapper — always use ./mvnw

mvnw is a script committed into the project that downloads the correct Maven version automatically. It is why anyone can clone the repo and build without installing Maven first. ./mvnw beats mvn every time.

The ./ is not decoration: it tells the shell to look in this exact directory rather than searching PATH. That is why it only works from the folder containing it.

1.4 Node and npm

Same LTS reasoning as Java. Node 26 was the newest release; Node 24 was the current Active LTS, so we used 24. npm is the package manager; package.json is the manifest; node_modules is where the resolved graph lands (and is never committed).

2 · Docker

The single most important infrastructure concept in the project, and the one that transfers to every job you will ever have.

2.1 The problem it solves

Every developer has said this sentence: "But it works on my machine." The code runs locally and breaks on the server — different OS, different library version, different config. Hours die here.

Analogy — the shipping container

Before the 1950s, cargo ships were loaded with loose goods: barrels, sacks, crates, all different shapes. Every port needed different equipment, every transfer was slow and manual, and loading a ship took days.

Then came the standard shipping container. Suddenly it didn't matter whether it held bananas or televisions — every container was the same size with the same fittings, so every crane, ship, truck and train handled it identically. This single boring invention is credited with reshaping global trade.

Docker is that container, for software. You package your app plus its exact dependencies plus its config into one standard unit. Every machine that can run containers runs yours identically. The host does not need to know or care what is inside.

2.2 Container vs virtual machine

You will be asked this in interviews.

Virtual machineContainer
Shipsan entire operating systemyour app and its libraries
Sizegigabytesmegabytes
Start timetens of secondsabout a second
Kernelits ownshares the host's
Analogy

VM = building a separate house for each tenant, each with its own foundation, plumbing and wiring.
Container = apartments in one building, sharing the foundation and plumbing, but with locked doors and fully separate living space.

Containers give you most of the isolation at a tiny fraction of the cost. That trade-off is why the entire cloud industry runs on them.

The follow-up that separates candidates

"Containers share the host kernel" is the textbook line. Here is the answer of someone who has actually used it:

Containers need a Linux kernel. macOS does not have one. So on a Mac, Docker always runs a hidden Linux VM, and your containers run inside that. Docker Desktop hides this so thoroughly that many developers don't know. Colima makes it explicit — colima start literally starts that VM.

We proved it: running docker info on a Mac reported Operating System: Ubuntu 24.04.4 LTS.

2.4 Docker Compose — declaring a whole stack

Our real docker-compose.yml, annotated:

    container_name: reconpilot-postgres   # fixed name, so docker exec is predictable

      POSTGRES_PASSWORD: localdev

      - "5432:5432"                # HOST port : CONTAINER port
    volumes:
      - pgdata:/var/lib/postgresql/data   # persist data outside the container
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U reconpilot -d reconpilot"]
      interval: 5s
      retries: 10

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

volumes:
  pgdata:                          # declares the named volume used above
Note there is no version: key

It was removed in Compose v2 and now produces a warning. Most tutorials online still include it.

Ports

A container has its own private network. "5432:5432" maps your Mac's port 5432 to the container's 5432, which is how Spring Boot running on your Mac reaches Postgres inside the container. The two numbers need not match: "5433:5432" would let you run a second Postgres without a clash.

Volumes — containers are disposable, data is not

Analogy

A container is a hotel room. When you check out it is wiped clean. A volume is the luggage you take with you — it exists independently of any room.

docker compose down      # stop and remove containers — volume SURVIVES
docker compose down -v   # ...and DELETE the volume. Data is genuinely gone.

Healthchecks — "running" is not "ready"

Postgres takes a few seconds to initialise after the process starts. Without a healthcheck, your app starts, tries to connect, and fails — intermittently, which is worse than failing always. The healthcheck polls until the database genuinely answers, so Compose reports (healthy) rather than leaving you to guess.

3 · PostgreSQL

Most of the hard thinking in ReconPilot is in the database. Not because the queries are complex, but because correctness, history and isolation are all enforced here rather than hoped for in application code.

3.1 Money must be integers

This is the single most important rule in financial software, and it is easy to get wrong because the wrong way appears to work.

The demonstration we ran on your machine

--- The classic ---
0.1 + 0.2 = 0.30000000000000004
Is it 0.3? false

--- 100,000 transactions of ₹3,333 at 0.4% ---
double : 1333200.0000005632
paise  : 133300000 paise = 1333000.00
exact  : 1333000.00

Why 0.1 + 0.2 ≠ 0.3

Computers store numbers in binary. Some decimals have no exact binary form — exactly as ⅓ has no exact decimal form (0.3333… forever). 0.1 in binary repeats forever, so the computer stores the nearest representable value. Add two approximations, get an approximation.

This is not a Java bug. It is IEEE 754, and it behaves identically in Python, JavaScript, C# and every other language.

There are TWO bugs in that output, not one

Conflating them is a mistake. The trailing 0.0000005632 is floating-point error — small, but it means you can never compare money with ==, and in a reconciliation product comparing amounts is the entire product.

The ₹200 gap is not float error at all. It is a rounding decision: 0.4% of ₹3,333 is ₹13.332, and whether that becomes ₹13.33 or keeps the fraction changes the total at scale.

Integers do not eliminate the rounding decision. They force you to make it once, explicitly, and apply it identically every time. Floats make the decision for you, silently, differently depending on the values. That inconsistency is the real crime, not the imprecision.

The rule

amount_paise  BIGINT NOT NULL CHECK (amount_paise >= 0)

All money is BIGINT paise. Never float, double, REAL or DOUBLE PRECISION. Where division is unavoidable, use BigDecimal with an explicit RoundingMode defined in exactly one place. BIGINT holds about 9.2 × 1018 paise, far beyond any plausible transaction.

Convert at the boundary only — when parsing input and when rendering output. Those two points are where bugs concentrate, so they get concentrated tests.

3.2 Two kinds of time — bi-temporal modelling

Almost nobody gets this right, and it is what makes audit possible.

occurred_at   TIMESTAMPTZ NOT NULL,   -- when the payment actually happened
recorded_at   TIMESTAMPTZ NOT NULL    -- when OUR SYSTEM learned about it
Analogy

A transaction happened on 3 March. The settlement file carrying it reached you on 10 March.

If someone asks "what did you believe on 5 March?", the honest answer must exclude that transaction — on the 5th you genuinely did not know about it. One timestamp cannot express that; two can.

-- what is true now
SELECT ... WHERE occurred_at BETWEEN ? AND ?

-- what we BELIEVED at time T  (this is the one that matters in a dispute)
SELECT ... WHERE occurred_at BETWEEN ? AND ? AND recorded_at <= T
One recorded_at per file, not per row

Every row from one ingestion shares a single recorded_at. We verified this: SELECT count(DISTINCT recorded_at) over 2,000,000 rows returned 1.

Calling now() per row would smear one file across time, so a replay filtered on recorded_at could include half a file — and "what did we know at 10:31" would have no meaningful answer.

3.3 Store facts, derive answers — event sourcing

The instinct is to keep a running total:

merchant.monthly_total += transaction.amount;   // every problem lives here

One mutable number. No history, no ordering, no explanation. It cannot be replayed, audited or corrected.

Analogy — your bank statement

Your bank does not store only your balance. It stores every transaction, and the balance is derived. That is why you can dispute a charge from three years ago. If banks stored only the current balance, no dispute could ever be settled.

So transaction_event is append-only: no UPDATE, no DELETE. A restatement from a PSP arrives as a new row with the same external_txn_id and a later recorded_at. The current view is the greatest recorded_at; the historical view is the greatest recorded_at <= T.

Truth vs cache

TRUTH (append-only, never changes)   CACHE (drop and rebuild anytime)
├── transaction_event                ├── merchant_month_total
├── merchant_category_event          ├── mdr_calculation
└── ingestion_batch                  └── Redis projections

Everything on the right can be deleted and regenerated from the left. That is not merely a nice property — it is a testable one: rebuild the projections from scratch, compare to the live ones, and any difference is a bug.

3.4 Indexes — what they cost

Analogy

An index is the index at the back of a textbook. Without it, finding "idempotency" means reading every page. With it, you look up one entry and jump straight there.

But the index took paper to print, and every time the book changes, the index must be reprinted. That is exactly the trade: faster reads, slower writes, more storage.

We measured it on 2,000,000 real rows:

ComponentSizeShare
Table data522 MB60%
Indexes349 MB40%
Total871 MB456 bytes/row
My estimate was 52% low

ADR 0002 estimated 300 bytes per row. Reality was 456 — because the estimate counted column data and ignored indexes entirely, which turned out to be 40% of storage. That is the classic estimation mistake.

But notice: the estimate was wrong in detail and right in decision. A single Postgres instance was still correct. Back-of-envelope arithmetic is for choosing an architecture, not for capacity planning.

3.5 Keyset pagination, not OFFSET

A classic interview question, and the reason "our admin page gets slow after page 50" is such a common bug report.

OFFSET 500000 LIMIT 5000   -- database reads 505,000 rows and throws away 500,000
WHERE id > ? LIMIT 5000     -- index seeks straight to the position
Analogy

OFFSET is counting pages from the front of the book every single time you want to continue reading. Keyset is a bookmark.

OFFSET degrades with every page because the database must count past everything it has already returned. Over a million rows that is quadratic work. Keyset remembers where it stopped, so page 200 costs what page 1 cost.

Our reconciliation walks a batch in 5,000-row keyset pages, which is how 1,000,000 rows scan in 3.0 seconds in a 256 MB heap. The index was widened to (batch_id, id) to support it.

Why chunks rather than one long cursor

A single streaming cursor also uses constant memory — but it holds one database transaction open for the entire run. Long transactions block vacuum, accumulate write-ahead log, and make the run all-or-nothing with no ability to resume. Chunking gives constant memory and short transactions.

3.6 Constraints beat code

Analogy

A sign saying "one person at a time" is application logic — it works until someone ignores it. A turnstile is a database constraint.

If a rule must never be violated, push it as far down the stack as it will go. Application code is where rules go to be forgotten, refactored away, or raced against.

Idempotency by unique constraint

UNIQUE (tenant_id, content_hash)   -- SHA-256 of the file's bytes

Upload the same file twice and PostgreSQL rejects it — not an if statement someone can forget. Measured: a duplicate 148 MB upload returned in 652 ms having written nothing.

Partial unique index — when the rule has an exception

CREATE UNIQUE INDEX uq_batch_content_not_failed
    ON ingestion_batch (tenant_id, content_hash)
    WHERE status <> 'FAILED';

"At most one non-failed batch per file, and any number of failed attempts." A plain unique constraint would block retrying a file that failed once, which means one transient error blocks it forever.

Found by the very first integration test

We changed the application's idempotency query to ignore FAILED batches, but left the constraint untouched. The code decided to retry; the database refused with a duplicate key.

The same rule was written in two places and only one was changed. A system that contradicts itself.

Upsert — let the database resolve races

INSERT INTO merchant (id, tenant_id, external_ref, display_name)
VALUES (?, ?, ?, ?)
ON CONFLICT (tenant_id, external_ref)
DO UPDATE SET display_name = merchant.display_name
RETURNING id

The apparently pointless DO UPDATE SET x = x is deliberate: DO NOTHING returns no rows, so RETURNING would yield nothing on conflict. Assigning the column to itself makes the conflicting row be returned.

This replaced a check-then-act race that failed 12 of 14 batches on the first concurrent run — covered in full in §8.

3.7 JSONB — keep the original, always

raw JSONB NOT NULL   -- the source row, verbatim

Every parse is a lossy interpretation. When a customer disputes a figure, you argue from what the PSP actually sent, not from your interpretation of it. Storage cost was 178 MB across 2,000,000 rows — being unable to prove your input is unbounded liability.

JSONB (binary JSON) is stored parsed and can be indexed; JSON stores the raw text. Prefer JSONB unless you need to preserve exact formatting and key order.

3.8 Row-level security — the feature that did nothing

RLS lets the database itself filter rows per user, so a forgotten WHERE clause cannot leak data.

Analogy

Application filtering is a receptionist checking badges. RLS is the floors being locked. For a multi-tenant financial product you want both, because one leak is company-ending.

Ours was enabled and completely inert 
relname           | rls_enabled | rls_forced
transaction_event | t           | f            ← enabled, NOT forced

current_user: reconpilot        ← also the table owner, and a superuser

SELECT count(*) FROM transaction_event;   -- no tenant set
-> 2000000                                 ← everything visible

Two independent exemptions, either of which disables RLS completely:

  1. PostgreSQL exempts a table's owner unless FORCE is also set.
  2. A superuser bypasses RLS entirely, even with FORCE.

The app connected as a role that was both. The policies were syntactically perfect and never consulted.

A security control that is enabled but not enforced is worse than none, because it creates false confidence. The schema reads as though isolation is handled. A reviewer would believe it.

The fix needs every part

-- 1. a least-privilege role: neither owner nor superuser
CREATE ROLE reconpilot_app LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO reconpilot_app;

-- 2. force RLS so it applies to the owner too
ALTER TABLE transaction_event FORCE ROW LEVEL SECURITY;

-- 3. policies that govern reads AND writes
CREATE POLICY tenant_isolation ON transaction_event
    USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
PieceWhy it is not optional
FORCEWithout it the owner bypasses every policy.
Non-superuser roleA superuser bypasses RLS even with FORCE. This is a precondition, not hardening.
WITH CHECKUSING governs reads only. Without this a tenant could write rows carrying another tenant's id — writable but invisible, which is worse than readable.
, true"missing_ok": returns NULL when unset rather than raising an error.
NULLIF(…, '')Cleared settings become '', and ''::uuid raises. NULLIF collapses both cases to NULL, and a NULL comparison is never true — so "no tenant" means "no rows", which is the safe default.

The proof

reconpilot_app, no tenant set  →    0 rows
reconpilot_app, tenant = Acme  →  300 rows
reconpilot_app, tenant = Globex → 120 rows
knowing another tenant's row id →    0 rows

3.9 Connection pooling, and the leak it creates

Opening a database connection is slow — TCP handshake, authentication, session setup. So Spring opens a handful up front and reuses them. That is HikariCP, and "why pool connections?" is a common interview question: because the handshake costs more than the query.

Pooling and session variables are a dangerous combination

A PostgreSQL session variable set on a pooled connection stays on it when it returns to the pool. The next request to borrow that connection inherits the previous request's tenant.

That is a cross-tenant data leak caused by an optimisation that has nothing to do with tenancy — and it would be completely silent.

Our defence is doubled on purpose: set the tenant on every checkout (so whatever the last borrower left is overwritten) and clear it on close (so nothing goes back carrying state). Either alone would suffice in the normal path; both are there because the failure is silent and severe.

3.10 Flyway — migrations as version control for the schema

V1__initial_schema.sql
V2__batch_lifecycle_columns.sql
V3__recon_break_idempotency.sql
V4__allow_retry_of_failed_batches.sql
V5__dispute_workflow.sql
V6__auth_and_enforced_tenant_isolation.sql

The filename is a convention: V<version>__<description>.sql with two underscores. Flyway applies them in order and records each in flyway_schema_history, so it never runs one twice.

Two settings that matter 
spring.flyway.enabled=true
spring.jpa.hibernate.ddl-auto=validate

Flyway owns the schema. Hibernate only checks it. validate means Hibernate compares your entities to the schema and complains if they disagree, but never alters anything.

The tempting alternative, ddl-auto=update, lets Hibernate silently change your production schema based on your Java classes. Never do that. "Flyway owns schema, Hibernate validates only" is the answer an interviewer wants.

Migrations run as the owner; the application runs as the least-privilege role. Splitting them is the point — with one all-powerful connection, RLS cannot work at all.

Spring is large, but it rests on a small number of ideas. Understand those five and the rest is vocabulary.

4.1 Inversion of Control — the one idea everything else sits on

Normally your code decides what it needs and creates it:

class OrderService {
    private final EmailSender email = new SmtpEmailSender("smtp.gmail.com", 587);
    //                                ↑ this class now DEPENDS on SMTP forever
}

Want to test it without sending real email? You can't. Want to swap to SendGrid? Edit the class.

Analogy — hiring

Without IoC: every employee recruits their own assistant, negotiates their salary and buys their laptop. Chaos, and nobody can be replaced.

With IoC: HR hires people and hands each employee whoever they need. The employee says "I need an assistant" and one arrives. Swapping assistants is HR's problem, not theirs.

Spring is HR. "Inversion of control" means the control over who creates what is inverted — moved out of your class and into the framework.

class OrderService {
    private final EmailSender email;
    OrderService(EmailSender email) { this.email = email; }   // just ask
}

Now the class works with any EmailSender. In a test you pass a fake. In production Spring passes the real one. This is dependency injection, and it is why Spring code is testable.

4.2 Beans — the objects Spring manages

The framework should know about your domain. Your domain should not know about the framework.

That is dependency inversion, the core idea behind hexagonal and clean architecture.

Constructor injection, always

One constructor means Spring needs no annotation to know what to inject. Fields can be final, so the object cannot exist in a half-built state, and the dependencies are visible in the signature. Field injection (@Autowired on a field) hides them and makes the class untestable without Spring.

4.3 Auto-configuration — and how adding a bean can remove one

Spring Boot looks at your classpath and configures things automatically. Jackson present? JSON conversion is wired. A JDBC driver and a URL? A DataSource and a JdbcTemplate appear.

It does this with conditional configuration — most importantly:

@ConditionalOnMissingBean(JdbcOperations.class)   // "only if the user hasn't made one"
This cost us hours, and it is a genuinely great interview story

We declared an admin JdbcTemplate for cross-tenant system work. Spring Boot saw a JdbcOperations bean already existed and silently stopped creating the normal one.

Result: every controller and service got the privileged template. Row-level security worked perfectly at the database level and applied to nothing, because no application query ever reached it.

Adding a bean removed another one. No warning. The app started fine. The tests passed. Only an end-to-end check with two real tenants exposed it.

The fix: declare the normal one explicitly and mark it @Primary.

4.4 Proxies — the trap in @Async, @Transactional and @Cacheable

How does @Transactional actually start a transaction? Spring wraps your bean in a proxy — a stand-in object that looks identical from outside but does extra work before and after each call.

Analogy — the receptionist

A receptionist sits outside your office. Visitors from outside must pass them, and the receptionist says "he's busy — I'll put this in his inbox for later" (that is the async behaviour).

But if you are already inside the office and walk to the next desk, you never pass the receptionist. You just interrupt that person directly — synchronously.

class Service {
    void submit() {
        this.process();      // ← runs RIGHT NOW. @Async is silently ignored.
    }
    @Async
    void process() { /* long work */ }
}
Nothing warns you

It compiles, the annotation is right there, and it simply is not async. That is why IngestionWorker is a separate bean — the call comes from outside, so it passes the proxy.

The same trap applies to @Transactional and @Cacheable. This is one of the most common Spring interview questions.

4.9 Asynchronous work and bounded capacity

@Bean("ingestionExecutor")
public ThreadPoolTaskExecutor ingestionExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(2);
    ex.setMaxPoolSize(4);
    ex.setQueueCapacity(10);
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
    return ex;
}
Analogy — the restaurant

2 cooks normally, up to 4 when busy, 10 seats in the waiting area.

No limit on cooks → hire one per order → 10,000 cooks → the restaurant collapses.
No limit on seats → accept every booking forever → the building falls down. This one is nastier, because it looks fine for hours, then dies of an OutOfMemoryError far from the actual cause.

A genuine surprise in ThreadPoolTaskExecutor

It fills the queue before hiring extra threads:

2 threads busy  →  next tasks go on the queue (up to 10)
queue full      →  NOW create threads 3 and 4

Most people assume it grows the pool first. It does not. So with a 10-slot queue, thread 4 does not appear until 12 tasks are outstanding.

AbortPolicy, not CallerRunsPolicy

CallerRuns hands the work back to the HTTP thread — silently restoring the synchronous behaviour we removed, at the exact moment the system is busiest. The counter stops being served entirely.

Abort surfaces overload honestly as 503 and lets the client retry. Measured: 16 concurrent uploads against a capacity of 14 produced exactly 14 accepted, 2 rejected. That is backpressure — a system that knows its own limit and says so.

4.10 Spring Security and JWT

What a JWT actually is

Three base64 segments: a header, a payload of claims, and a signature over the first two.

The payload is encoded, not encrypted

Anyone holding the token can read it. What the signature guarantees is that nobody has changed it without the secret. So a token may carry an id and a role, and must never carry a secret.

Analogy — sessions vs tokens

Session id = a cloakroom ticket. The number means nothing by itself; the cloakroom must remember which coat it maps to. Every attendant needs the same list.

JWT = a signed, tamper-evident boarding pass. Everything needed is printed on it, and the signature proves it is genuine. Any gate can check it with no lookup and no shared store.

The cost: a boarding pass cannot be un-issued. Until it expires it stays valid, even if the passenger is banned — which is why expiry is short and instant revocation needs a denylist on top.

Password hashing

@Bean PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

BCrypt, never SHA-256 or MD5. Fast hashes are the wrong tool for passwords precisely because they are fast — a GPU tries billions of guesses per second. BCrypt is deliberately slow, its cost is tunable upward as hardware improves, and it salts each password so two users with the same password get different hashes, which defeats precomputed rainbow tables.

The filter chain

.csrf(csrf -> csrf.disable())                       // no cookies = no CSRF vector
.sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .requestMatchers("/actuator/health").permitAll()
    .anyRequest().authenticated())                  // DEFAULT DENY
.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
Default deny

anyRequest().authenticated() means a new endpoint is protected because nobody remembered to open it, rather than exposed because nobody remembered to close it. Always order your rules that way.

Two security details worth stating in an interview

  • The tenant comes from the signed token, never from a parameter. A ?tenantId= parameter would let anyone read anyone's data by editing a URL — among the most common multi-tenant vulnerabilities there is.
  • Unknown email and wrong password return the same 401. Distinguishing them turns the login form into a way to discover which email addresses have accounts.

ThreadLocals and why they must be cleared

try {
    // ... establish tenant from token, handle request
} finally {
    TenantContext.clear();
    SecurityContextHolder.clearContext();
}

Request threads are pooled and reused. A tenant left in a ThreadLocal becomes the next request's tenant — a cross-tenant leak arising from thread reuse rather than from any mistake in business logic.

A ThreadLocal does not cross a thread boundary

The ingestion worker runs on a pool thread, where the request thread's ThreadLocal is simply absent. That is why the tenant id is passed to it as an explicit parameter and re-established at the start of the task.

5.3 The test that destroyed a database

This is the most important lesson in the chapter

@ServiceConnection only overrides spring.datasource.*. Our hand-rolled app.datasource.admin.* kept pointing at localhost:5432/reconpilot — the real development database — and clearDatabase() ran TRUNCATE ... CASCADE against 1,000,000 rows of real data.

A test suite that can reach your development database will eventually destroy it. Not might — will.

There was a second cause underneath: replacing Spring Boot's auto-configured DataSource with a hand-built one silently disconnects @ServiceConnection entirely, because Testcontainers contributes a JdbcConnectionDetails bean that only the auto-configured DataSource consumes.

The fix, in two layers

registry.add("app.datasource.admin.url", postgres::getJdbcUrl);
registry.add("spring.flyway.url",        postgres::getJdbcUrl);

// 2. refuse to run against anything else
if (!url.equals(postgres.getJdbcUrl())) {
    throw new IllegalStateException("Refusing to run: not the test container");
}
A destructive operation should verify what it is about to destroy, rather than trust that the wiring is right.

Verified with a canary row in the dev database that survived a full suite run.

5.4 Test-first, and why it actually matters

We wrote the MDR tests from the regulator's published figures before the calculator existed. One failed:

capBindsExactlyAtSeventyFiveThousand

₹74,999 × 0.4% = ₹299.996, which HALF_UP rounds to ₹300 — exactly the cap. My assumption was wrong; the code was right.

Why writing the test first mattered here

Had I written the code first and the test after, I would have run the calculator, seen ₹300, thought "right, that's what it does", and asserted ₹300. The test would have passed and taught me nothing.

Tests written after the code tend to encode the code's behaviour rather than the requirement — so they lock in bugs instead of catching them.

It also found something real: the percentage and the cap interact through the rounding mode. Nobody could predict that by reading the regulation.

6.2 CORS, and why we avoided it entirely

What CORS actually is

Your React app runs at localhost:5173. Your API is at localhost:8080. To a browser those are different origins, and it will refuse the request unless the server explicitly opts in with CORS headers.

This is a browser safety rule, not a server one — curl is unaffected, which is why an API can work perfectly in a terminal and fail in a browser.

server: {
  proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } }
}

Now the browser sees one origin, so the problem does not arise. And it mirrors production, where a single reverse proxy serves both. Sidestepping a problem is often better than configuring around it.

7.2 Back-of-envelope estimation

1,000 merchants × 1,000 transactions/month = 1,000,000/month = 12,000,000/year

average write rate  = 1,000,000 ÷ (30 × 86,400) ≈ 0.4 writes/second
peak (1M in 1 hour) = 1,000,000 ÷ 3,600          ≈ 280 writes/second

Read those numbers and stop

0.4 writes per second. A single PostgreSQL instance handles this without effort, for years. No sharding. No microservices. No Kubernetes. No read replicas.

This is not a scale problem. It is a correctness problem.

Ask a junior to design this and you get microservices, Kafka everywhere and a service mesh — architecture cargo-culted from blog posts about Netflix. Netflix has that architecture because Netflix streams to 300 million people. You have 0.4 writes per second.

Complexity is a budget. Spend it where the difficulty actually is.

A bridge that has held every truck you have driven over it is not rated for anything. It is untested.

The principle: memory use must be O(1), not O(n). "It works on my test file" is not a capacity statement.

7.4 Idempotency

Analogy

Pressing a lift button five times does not summon five lifts. The first press changes the state; the rest are no-ops. That is idempotency.

It matters because networks retry. A client sends a request, the response is lost, the client retries — and without idempotency you have ingested the file twice.

Ours is a SHA-256 of the file bytes under a unique constraint. Enforced by the database, not by an if. Three separate places in this project use the same pattern: file ingestion, break creation, and dispute creation.

3. AutoPay?            → ₹0
4. Merchant is P2PM?   → ₹0     ← MUST come before the amount check
5. Amount ≤ ₹2,000?    → ₹0
6. Otherwise by category
Specificity is not precedence

Given a ₹2,000 AutoPay payment to a fuel merchant who is P2PM, four rules fire. Three say ₹0 and one says ₹5. The instinct is "the most specific rule wins" — that is how CSS works. Here it is wrong.

Three rules produce ₹0, so the order looks academic. It is not: we have to explain the number. "₹0 because it is AutoPay" and "₹0 because the merchant is P2PM" have different lifespans — if the merchant is reclassified, the AutoPay reason survives and the P2PM reason evaporates.

Which rule fired is as important as what it produced.

7.6 State machines

DRAFT ─file→ FILED ─ack→ ACKNOWLEDGED ─accept→ ACCEPTED ─settle→ RECOVERED
   │            │              │
   └── withdraw ┴── reject ────┴─→ REJECTED / WITHDRAWN  (terminal)

The legal transitions live in the enum as data, not as if statements spread through a service:

ALLOWED.put(DRAFT,     EnumSet.of(FILED, WITHDRAWN));
ALLOWED.put(ACCEPTED,  EnumSet.of(RECOVERED));
ALLOWED.put(RECOVERED, EnumSet.noneOf(DisputeStatus.class));   // terminal

Three consequences: the whole lifecycle is readable in one place; adding a state forces you to declare its transitions; and an illegal transition becomes impossible by construction rather than merely unlikely.

The alternative — a mutable status string updated wherever convenient — is how records end up RECOVERED without ever having been FILED.

One gate. There is deliberately no /file, /accept, /reject endpoint: separate endpoints tempt each to do its own checking, and the fifth one, added in a hurry, forgets a rule the other four enforce.

7.7 Async, 202, and backpressure

Client                          Server
  │  POST /api/ingest             │
  │ ─────────────────────────────>│  parse 2,000,000 rows
  │         51 SECONDS            │  insert 2,000,000 rows
  │      thread blocked           │  ← one HTTP thread held the whole time
  │ <─────────────────────────────│

Four things are wrong, and none is about speed:

  1. Proxies and load balancers time out at 30–60 seconds — the request dies after most of the work.
  2. The client learns nothing until the end. No id, no progress, nothing to poll.
  3. A dropped connection strands the batch in PARSING forever.
  4. One upload occupies a request thread for a minute. Tomcat's pool is bounded (200 by default), so a handful of concurrent uploads stops the API answering anything — including health checks.

Point 4 turns a slow feature into an outage. The fix took the response from 51,018 ms to 657 ms.

202, not 200

200 claims a result the caller does not have. 202 Accepted says "valid, scheduled, not done", with a Location header pointing at where the answer will appear. Returning 200 for work that has not happened is a lie.

7.8 Caching is not always Redis

Map<String, UUID> merchantCache = new HashMap<>();

2,000,000 rows, 500 distinct merchants. A plain HashMap between the parser and the database eliminated 99.975% of the lookups. That is caching. No infrastructure required.

The general shape: identify repeated identical work, do it once, remember the answer. Redis matters when the cache must be shared between processes or survive a restart — not before.

7.9 Concurrency bugs are invisible until you run things concurrently

Thread A: SELECT merchant 'shop000@upi'  →  not found
Thread B: SELECT merchant 'shop000@upi'  →  not found   ← both looked first
Thread A: INSERT                          →  OK
Thread B: INSERT                          →  UNIQUE violation → whole batch dies

Both threads checked honestly. Both got a true answer. The answer simply stopped being true in the gap between checking and acting.

2,000,000 rows sequentially: fine. The first concurrent burst: 12 of 14 batches failed.

Any "check, then act" has a gap. If two things can run at once, something will eventually land in it. Make it one indivisible step instead.

7.10 Defence in depth

Two independent mechanisms for anything whose failure is catastrophic:

RiskLayer 1Layer 2
Cross-tenant data leakapplication filters by tenantPostgreSQL row-level security
Session variable leaking via poolset on every checkoutclear on close
Duplicate ingestionapplication checks the hashunique constraint
Illegal dispute transitionUI offers only legal buttonsserver returns 409

In each pair, layer 1 is convenience and layer 2 is correctness. Where the failure is silent and severe, the cost of the second layer is trivial compared with the cost of being wrong.

8 · Every bug, and what it taught

Ten real defects. For an interview, these are worth more than the features.

8.1 The rounding disaster — 8,174 false claims from one paise

D7 — the most expensive kind of bug

The first reconciliation found 15,474 breaks against 7,300 planted. Every extra one was a capital-markets row off by exactly one paise: expected 67, charged 66.

The generator truncated; the calculator rounds HALF_UP.

Had those been filed against a real PSP, every single one would have been wrong — and the product's entire premise, "our arithmetic is right and yours isn't", would have died on first contact with a customer.

We predicted this in writing four sessions earlier, in OPEN-QUESTIONS.md: "systematic rounding differences will surface as false breaks." That was a hypothesis. 8,174 is a measurement.

It is now a business control: reconpilot.claims.filing-enabled defaults to false, and the error message a user sees explains exactly why.

8.2 Security theatre — RLS enabled and inert

Covered in §3.8. The lesson: a security control that is enabled but not enforced is worse than none, because it creates false confidence. I wrote the ADR claiming defence in depth, and believed it until I tested it.

8.3 The test suite that destroyed the dev database

Covered in §5.3. A test suite that can reach your development database will eventually destroy it.

8.4 Adding a bean removed another one

Covered in §4.3. @ConditionalOnMissingBean means declaring an admin JdbcTemplate silently deleted the normal one, routing every query through the privileged connection.

8.5 A rejected upload poisoned its own retry

Two correct features, broken by their combination 
POST part05.csv  →  503 INGESTION_BUSY     ← honest, correct
POST part05.csv  →  200 alreadySeen: true  ← the file can NEVER be ingested

The batch row was written before the work was queued, so a rejection left it stranded in RECEIVED. Idempotency keys on the content hash, so that stranded row made every retry report "already ingested".

An honest rejection turned into silent, permanent data loss. Idempotency is correct. Rejecting when full is correct. Together they destroy data.

When you refuse a request, leave the world exactly as you found it. A refusal that changes state is not a refusal.

8.6 The check-then-act race

Covered in §7.9. Invisible over 2,000,000 sequential rows; failed 12 of 14 batches on the first concurrent run.

8.7 Tests that could never run

Covered in §5.1. *IT classes compiled and were silently skipped by Surefire.

8.8 The constraint that contradicted the code

Covered in §3.6. We changed the idempotency query to allow retrying FAILED batches, and left the constraint alone. The code decided to retry; the database refused.

The same rule written in two places will eventually be changed in one.

8.9 The IDE and the build using different JDKs

Covered in §1.2. JAVA_HOME in ~/.zprofile is invisible to /bin/sh. Lombok — which we were not even using — crashed on JDK 27. Removing an unused dependency eliminated a whole class of failure rather than pinning around it.

8.10 The API designed without a consumer

Found within minutes of writing the first screen

GET /api/breaks returned raw Map<String,Object> — leaking the database's snake_case naming into the API — and omitted the break's own id, so a client could display a finding but could not act on it.

An API designed without a consumer is one that technically works and is unusable.

The pattern across all ten

Not one of these would have been found by reading the code

Every single one was found by running something and checking a belief: firing 16 concurrent uploads, querying the database as a different role, planting known errors, putting a bug back to watch the test fail.

That is worth saying in an interview more plainly than any feature: "I stress-tested my own system and found these; here is what each one taught me."

Step 3 — Design before code

This is the step people skip, and it is the one that saved the most time.

  1. Requirements, split into functional and non-functional. Rank two of the non-functionals LOW on purpose.
  2. Scale estimation, out loud, with arithmetic. Ours said 0.4 writes/second — which decided the entire architecture: one Postgres, a modular monolith, no Kafka.
  3. Read the primary source. We designed a mid-month threshold engine from accurate news summaries. The regulator's own FAQ showed the mechanism was an account category with a three-month qualifying period. Had we coded first, we would have built the wrong thing and found out during customer disputes.
  4. Write ADRs. One file per decision: context, decision, consequences — including what you gave up.
Turn the regulation into a decision table, then into tests

Prose is ambiguous; tests are not. Ours cites the FAQ question each figure came from, so a disputed calculation is defended by pointing at the regulator's own document rather than at our code.

Step 4 — The schema

Write V1__initial_schema.sql. The non-negotiables:

  • All money BIGINT paise, with CHECK (x >= 0).
  • occurred_at and recorded_at on the event table.
  • raw JSONB NOT NULL — keep the source row verbatim.
  • Append-only: no UPDATE or DELETE on the event log, ever.
  • UNIQUE (tenant_id, content_hash) on batches for idempotency.
  • tenant_id on every tenant-scoped table.

Leave RLS until Step 10 — it needs authentication to be meaningful, and enabling it early breaks every test for no benefit.

Step 6 — The rules engine, test-first

Write the tests from the regulator's published figures before the implementation. Then:

  • Enums for every dimension (TxnType, PaymentRail, PayeeCategory).
  • Records for input and output — and put the rule id in the output, not just the amount.
  • One ordered evaluation method. Precedence is the contract.
  • Unspecified cases throw. Never guess a rate.
  • The rounding mode is a single named constant with a comment explaining it is provisional.
  • No Spring annotations in this class. Register it as a @Bean in a config class.
./mvnw test     # should be milliseconds, no Docker

Step 7 — Expose it, then add a UI for yourself

A thin @RestController that converts query parameters, delegates, and returns the record. Then a @RestControllerAdvice mapping your domain exceptions to honest status codes (501 for unspecified, 400 for bad input).

Add a root endpoint serving a small HTML index of worked examples. It costs twenty minutes and makes every subsequent change verifiable by clicking rather than by assembling URLs.

Step 8 — Ingestion

  1. Prove the memory problem first. Generate a 150 MB CSV, read it both ways under -Xmx128m, and watch one of them die. You will design differently afterwards.
  2. Parser returns a lazy Stream; hash the file through an 8 KB buffer. Never load it whole.
  3. Write with JdbcTemplate.batchUpdate, 1,000 rows per flush. Add ?reWriteBatchedInserts=true to the JDBC URL — free 28%.
  4. One recorded_at per file, computed once.
  5. Resolve merchants with INSERT ... ON CONFLICT ... RETURNING id, cached in a HashMap. Do not check-then-act.

Step 9 — Make it asynchronous

  • Synchronous part: validate header, hash, check idempotency, insert the batch row, return 202 with a Location header.
  • Asynchronous part: a separate bean annotated @Async — self-invocation bypasses the proxy.
  • Bound the pool: 2 core, 4 max, queue 10, AbortPolicy. Map the rejection to 503.
  • On rejection, delete the batch row. Otherwise the stranded row poisons every retry.
  • Re-establish the tenant inside the worker — a ThreadLocal does not follow work onto a pool thread.
  • A startup sweep marks batches left in RECEIVED/PARSING as FAILED, using the admin connection.

Then fire 16 concurrent uploads. That is how we found two bugs in ten seconds.

Step 10 — Reconciliation, and validating it honestly

  • Walk the batch in 5,000-row keyset pages (WHERE id > ? ORDER BY id LIMIT n), never OFFSET.
  • Index (batch_id, id) to support it.
  • Classification precedence: exempt, then cap breach, then overcharge, then undercharge.
  • Unique index on recon_break(transaction_event_id) plus ON CONFLICT DO NOTHING, so re-running cannot duplicate findings.
  • Unspecified rules are counted and skipped, never broken.
Validate with planted errors and an independent implementation

Generate the test file with a known number of deliberately corrupted rows, and compute the expected MDR with a second implementation you write by hand — not by calling the code under test. Ours disagreed by one paise and exposed 8,174 false breaks.

Step 11 — The dispute workflow

  • Transitions as data in the enum, with a completeness test over @EnumSource.
  • One transition endpoint, not five.
  • Append-only dispute_event table recording actor, note and timestamp.
  • Guards that encode business rules: an undercharge cannot be claimed; one claim per break; recovery cannot exceed the claim.
  • 409 for an illegal transition, 422 for a refused claim.

Step 12 — Authentication and real tenant isolation

Do this before building further on top, not after.

-- 1. a least-privilege role: neither owner nor superuser
CREATE ROLE reconpilot_app LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO reconpilot_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO reconpilot_app;

-- 2. force RLS so it applies to the owner too
ALTER TABLE transaction_event FORCE ROW LEVEL SECURITY;

-- 3. policies governing reads AND writes
CREATE POLICY tenant_isolation ON transaction_event
    USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);

On the Java side:

  1. Two datasources. App as reconpilot_app; Flyway and system tasks as the owner.
  2. Declare the primary JdbcTemplate explicitly and mark it @Primary — otherwise declaring an admin one silently deletes it.
  3. Honour JdbcConnectionDetails in your DataSource bean, or you disconnect Testcontainers and your tests will point at your dev database.
  4. A TenantAwareDataSource that sets the tenant on every checkout and clears it on close.
  5. JWT filter establishing the tenant from the signed token, clearing the ThreadLocal in a finally.
  6. BCrypt for passwords. Same 401 for unknown email and wrong password. 401 entry point, not 403.
Make the test suite prove it is talking to a container 
if (!url.equals(postgres.getJdbcUrl()))
    throw new IllegalStateException("Refusing to run: not the test container");

Add this before you write a single TRUNCATE. We added it afterwards, having lost a million rows.

Then write the isolation test that connects as the app role — a test running as the owner would pass while proving the opposite of what it claims.

10 · Interview answers

The short versions. Each one is backed by something you measured.

"Tell me about a project."

I built a reconciliation platform for India's new UPI MDR rules. It ingests settlement files — two gigabytes, millions of rows — independently recomputes what each merchant should have been charged under the NPCI framework, and drives the differences to recovery. On a million-row file it finds around 7,300 discrepancies worth ₹1.3 lakh in three seconds, in a 256 MB heap.

"How did you decide the architecture?"

I estimated first. A thousand merchants at a thousand transactions each is 0.4 writes per second average, 280 at peak, and about 5.5 GB a year. A single Postgres instance handles that for years. So this is not a scale problem, it is a correctness problem — and I spent the complexity budget on determinism and auditability rather than on distribution.

"Why not microservices?"

Because nothing in the numbers asked for them. They would have added network partitions, partial failures and eventual consistency to a system whose hard requirement is paisa-exact correctness. I built a modular monolith with enforced boundaries, so any module could be extracted later if a real reason appeared.

"How do you handle a 2 GB file?"

Stream it. I measured both ways: reading a 148 MB file whole used 251 MB of a 256 MB heap and died below that, because each line becomes a String object costing about 2.7× the file size. Streaming did the same work in 23 MB. Memory has to be independent of input size — the dangerous case is the one that almost fits, because it ships and then dies at 3 a.m. on your biggest customer's biggest file.

"How do you guarantee you don't double-process a file?"

A SHA-256 of the file bytes under a unique constraint, so Postgres rejects it rather than application code that someone can forget. A duplicate 148 MB upload returns in 652 milliseconds having written nothing. The same pattern appears three times in the system.

"Tell me about a bug you found."

I enabled row-level security for multi-tenant isolation, then tested whether it actually worked — and it did nothing. Postgres exempts a table's owner from RLS unless you also FORCE it, and exempts superusers entirely, and the app connected as both. Two million rows were visible with no tenant context. I'd written an ADR claiming defence in depth and believed it. The fix needed a least-privilege role, FORCE, and WITH CHECK on the policies — USING alone governs reads, so a tenant could otherwise write rows it couldn't see.

"Tell me about a concurrency bug."

Merchant creation was a check-then-act: SELECT, then INSERT if absent. Two million rows sequentially never hit it. The first burst of 16 concurrent uploads failed 12 of 14 batches with a duplicate key. I replaced it with an atomic INSERT … ON CONFLICT … RETURNING, letting Postgres resolve the race. The lesson is that any check-then-act has a gap, and something will eventually land in it.

"How do you know your tests are any good?"

I put the bugs back and watched the tests fail, then restored the fixes. A regression test that has never failed is a hypothesis, not a test. I also validated the detection engine by planting a known number of errors — 7,300 — and requiring it to find exactly those, with the expected values computed by a second implementation I wrote by hand. That caught a one-paise rounding disagreement that was producing 8,174 false claims.

"What's the hardest part of the domain?"

Rounding. The regulator publishes 0.4% but never states a rounding rule. One paise of disagreement between our arithmetic and a PSP's produces thousands of false claims — and the product's whole premise is that our arithmetic is right. So filing is disabled by default in code, and the error message explains why. That's an engineering measurement turned into a business control.

"What would you do differently or next?"

Three things. Generate the TypeScript types from an OpenAPI spec instead of mirroring them by hand. Move the ingestion queue outside the process — not for throughput, which we don't need, but so work survives a restart. And add the AI layer for normalising PSP statement formats, which is the part that doesn't generalise well in code.
The sentence to end on

Most candidates describe features they built. The stronger move is to describe beliefs you tested and found false — the security control that did nothing, the test suite that destroyed a database, the rounding difference that would have destroyed customer trust. That is what senior engineering actually looks like, and very few people at two years' experience can show it.
