## 1. Data types that matter

### Money — never a floating type

```sql
-- ❌
amount NUMERIC(12,2)     -- workable, but slower and easy to misuse
amount REAL              -- ☠️ 0.1 + 0.2 ≠ 0.3

-- ✅ what ReconPilot uses
amount_paise BIGINT NOT NULL
```

Integer minor units are exact, fast, and index well. Format at the edge for
display, never in the database.

`NUMERIC`/`DECIMAL` is exact too and is the right choice when you genuinely need
fractional units or very large magnitudes — it is arbitrary precision, stored as
digits, and slower than an integer.

> **Postgres has a `money` type. Do not use it.** Its precision depends on a
> server locale setting, which means the same value means different things on
> different servers.

### Timestamps

```sql
occurred_at TIMESTAMPTZ NOT NULL      -- ✅ always this
recorded_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

- **`TIMESTAMPTZ`** stores an absolute instant (UTC internally) and converts on
  the way out using the session's timezone.
- **`TIMESTAMP`** (without time zone) stores a wall-clock reading with no idea
  which clock. Two servers in different regions will disagree about what it
  means.

**Use `TIMESTAMPTZ` unless you are storing something genuinely timezone-less**,
like a birthday.

### UUID vs BIGSERIAL

| | `BIGSERIAL` | `UUID` |
|---|---|---|
| Size | 8 bytes | 16 bytes |
| Generated by | the database | anywhere, including the client |
| Guessable | ✅ sequential — leaks volume | ❌ random |
| Index locality | excellent (appends) | poor (random inserts) |
| Merging datasets | collides | safe |

ReconPilot uses `UUID` because a batch id is created by the application before
the row exists, and because a sequential id in a URL tells a competitor how
many customers you have.

> The index-locality problem is real: random UUIDs scatter inserts across the
> whole B-tree instead of appending to one page. **UUIDv7** (time-ordered) fixes
> this and is worth naming if asked — it keeps uniqueness while restoring
> append-like behaviour.

### JSONB

```sql
mapping JSONB NOT NULL

SELECT mapping->>'txn_id' FROM format_mapping;         -- ->> gives text
SELECT mapping->'columns'->>0 FROM format_mapping;     -- ->  gives json
WHERE mapping @> '{"version": 2}'                      -- containment
CREATE INDEX ON format_mapping USING GIN (mapping);    -- index for @> and ?
```

**`JSONB` not `JSON`.** `JSON` stores the raw text and re-parses on every read;
`JSONB` stores a parsed binary form, which is faster, deduplicates keys, and is
the only one that can be indexed with GIN.

> **When to use it:** genuinely variable structure — a captured API payload, a
> per-customer field map. **When not to:** as a way to avoid designing a schema.
> Columns give you types, constraints, and a planner that understands them.

## 2. Keys and constraints

```sql
CREATE TABLE recon_break (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id      UUID NOT NULL REFERENCES tenant(id),
    batch_id       UUID NOT NULL REFERENCES ingestion_batch(id) ON DELETE CASCADE,
    break_type     TEXT NOT NULL CHECK (break_type IN
                     ('CHARGED_WHEN_EXEMPT','CAP_BREACHED','OVERCHARGED','UNDERCHARGED')),
    delta_paise    BIGINT NOT NULL,
    external_txn_id TEXT NOT NULL,

    UNIQUE (tenant_id, batch_id, external_txn_id)   -- idempotency, enforced here
);
```

| Constraint | Guarantees |
|---|---|
| `PRIMARY KEY` | unique + not null; one per table |
| `UNIQUE` | no duplicates (multiple NULLs are allowed!) |
| `FOREIGN KEY` | the referenced row exists |
| `CHECK` | an arbitrary boolean per row |
| `NOT NULL` | presence |

> **`UNIQUE` and NULL:** in standard SQL, `NULL` is not equal to anything —
> including another `NULL` — so a unique constraint permits **many** NULL rows.
> If you need "at most one row with no value", use a partial unique index:
>
> ```sql
> CREATE UNIQUE INDEX one_active_per_break
>     ON dispute (break_id) WHERE status <> 'WITHDRAWN';
> ```

### Put constraints in the database, not only in code

Application-level validation protects the happy path. The database protects
against every path: a second instance of your service, a migration script, a
DBA with `psql`, a race between two concurrent requests. **The constraint is
the only thing that is actually true.**

ReconPilot's `UNIQUE (tenant_id, batch_id, external_txn_id)` is what makes
ingestion idempotent — not the Java code that checks first.

### ON DELETE behaviour

```sql
REFERENCES batch(id) ON DELETE CASCADE      -- delete children too
REFERENCES batch(id) ON DELETE RESTRICT     -- refuse if children exist (default: NO ACTION)
REFERENCES batch(id) ON DELETE SET NULL     -- orphan them deliberately
```

`CASCADE` is convenient and dangerous — one `DELETE` can silently remove
millions of rows. Use it where the child genuinely cannot exist alone.

## 3. Indexes

### The mental model

An index is a **sorted copy of one or more columns, plus a pointer to the row**.
Like the index at the back of a book: finding "MVCC" means a binary search
through sorted entries, not reading every page.

```sql
CREATE INDEX idx_break_tenant_delta ON recon_break (tenant_id, delta_paise DESC);
```

### What they cost

Indexes are not free:

- **Storage.** Measured on this project: indexes were about **40% of total
  storage**.
- **Write speed.** Every `INSERT`, `UPDATE` and `DELETE` must update every index.
- **Maintenance.** More to vacuum, more to keep in cache.

> **The rule:** index what you filter, join or sort by. Do not index "just in
> case". An unused index is pure cost, and you can find them:
>
> ```sql
> SELECT relname, indexrelname, idx_scan
>   FROM pg_stat_user_indexes WHERE idx_scan = 0;
> ```

### Composite indexes and the leftmost prefix rule

```sql
CREATE INDEX idx ON recon_break (tenant_id, break_type, delta_paise);
```

This index can serve:

```sql
WHERE tenant_id = ?                                  -- ✅ leftmost
WHERE tenant_id = ? AND break_type = ?               -- ✅ leftmost two
WHERE tenant_id = ? AND break_type = ? AND delta_paise > ?  -- ✅ all three
```

But **not**:

```sql
WHERE break_type = ?                                 -- ❌ skips the leftmost column
WHERE delta_paise > ?                                -- ❌
```

**Column order matters.** Think of a phone book sorted by (surname, first
name): brilliant for "all the Jadhaos", useless for "everyone called Vaibhav".

> **Ordering guidance:** equality columns first, then range columns, then the
> sort column. A range predicate stops the index being useful for anything to
> its right.

### Index types

| Type | For |
|---|---|
| **B-tree** (default) | `=`, `<`, `>`, `BETWEEN`, `IN`, `ORDER BY`, prefix `LIKE 'abc%'` |
| **GIN** | `JSONB` containment, array membership, full-text search |
| **GiST** | geometric data, ranges, nearest-neighbour |
| **BRIN** | huge tables physically ordered by the column (time-series) — tiny index |
| **Hash** | equality only; rarely worth it over B-tree |

### Partial indexes

```sql
-- Index only the rows anyone actually queries
CREATE INDEX idx_open_disputes ON dispute (tenant_id)
    WHERE status NOT IN ('RECOVERED', 'REJECTED', 'WITHDRAWN');
```

Smaller, faster, cheaper to maintain. Ideal when queries always carry the same
filter — open items, active users, unprocessed rows.

### Covering indexes

```sql
CREATE INDEX idx ON recon_break (tenant_id) INCLUDE (delta_paise, break_type);
```

If every column a query needs is in the index, Postgres never touches the table
— an **index-only scan**. Shows in `EXPLAIN` as `Index Only Scan`.

### Why your index is being ignored

```sql
-- ❌ a function on the column defeats the index
WHERE lower(email) = 'a@b.com'
-- ✅ index the expression instead
CREATE INDEX ON app_user (lower(email));

-- ❌ leading wildcard
WHERE name LIKE '%recon'        -- cannot use a B-tree
-- ✅
WHERE name LIKE 'recon%'

-- ❌ type mismatch forces a cast
WHERE id = '123'                -- id is BIGINT, '123' is text

-- ❌ the planner decides a sequential scan is cheaper
--    On a small table, or when a query returns most rows, it is RIGHT.
```

That last point matters: **an index is not always faster.** Reading 80% of a
table through an index means random I/O for nearly every page, which is slower
than reading the whole thing sequentially. The planner knows this. Trust it —
after checking your statistics are fresh (`ANALYZE`).

## 4. Reading a query plan

```sql
EXPLAIN ANALYZE
SELECT break_type, count(*), sum(delta_paise)
  FROM recon_break
 WHERE tenant_id = '...'
 GROUP BY break_type;
```

- `EXPLAIN` — the plan the planner *would* use, with estimates.
- `EXPLAIN ANALYZE` — **actually runs it** and shows real times and row counts.
- `EXPLAIN (ANALYZE, BUFFERS)` — adds cache hits versus disk reads.

⚠️ `EXPLAIN ANALYZE` on an `UPDATE` or `DELETE` **performs it.** Wrap it in a
transaction and roll back.

### The node types

| Node | Meaning |
|---|---|
| `Seq Scan` | read the whole table |
| `Index Scan` | walk the index, then fetch rows |
| `Index Only Scan` | everything came from the index ✅ |
| `Bitmap Heap Scan` | many index matches, batched into page order |
| `Nested Loop` | for each outer row, probe the inner — good for small outer |
| `Hash Join` | build a hash of one side — good for large unsorted sets |
| `Merge Join` | both sides sorted — good when they already are |
| `Sort` | ⚠️ check whether it spilled to disk |

### What to look for

```
Seq Scan on recon_break  (cost=0.00..18334.00 rows=1000000 width=64)
                         (actual time=0.015..231.4 rows=1000000 loops=1)
```

1. **Estimated rows vs actual rows.** A large gap means stale statistics — run
   `ANALYZE`. The planner makes bad choices from bad estimates.
2. **A `Seq Scan` on a big table** with a selective filter — a missing index.
3. **`Sort Method: external merge Disk`** — the sort spilled; raise `work_mem`
   or index the sort column.
4. **`loops=N` where N is large** — a nested loop probing many times; often the
   SQL equivalent of N+1.

## 5. MVCC — how Postgres does concurrency

**MVCC = Multi-Version Concurrency Control.** The single most important thing
to understand about PostgreSQL.

### The idea

Postgres never overwrites a row in place. An `UPDATE` writes a **new version**
and marks the old one as dead. Each version carries the transaction ids that
created and deleted it (`xmin`, `xmax`).

Every transaction sees a **snapshot**: the versions that were committed when it
started (or when its statement started, depending on isolation level).

### Why this is a big deal

> **Readers never block writers, and writers never block readers.**

In a lock-based database, a long report blocks updates to the rows it reads. In
Postgres it does not — the report keeps reading its snapshot while updates
create new versions alongside.

### The costs

1. **Dead rows accumulate.** Old versions remain until vacuumed. A table updated
   heavily can grow far beyond its live data. This is **bloat**.
2. **`count(*)` is not free.** There is no single row count, because the visible
   count depends on *your* snapshot. Postgres must scan.
3. **Long transactions are expensive.** An open transaction stops vacuum from
   removing any version newer than its snapshot — everywhere in the database,
   not just its own tables. An idle-in-transaction connection is a genuine
   production hazard.

```sql
-- find them
SELECT pid, state, age(clock_timestamp(), query_start), query
  FROM pg_stat_activity
 WHERE state = 'idle in transaction'
 ORDER BY 3 DESC;
```

## 6. Transactions and isolation

```sql
BEGIN;
  UPDATE account SET balance = balance - 100 WHERE id = 1;
  UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;                     -- or ROLLBACK
```

### The anomalies

| Anomaly | What happens |
|---|---|
| **Dirty read** | you read uncommitted data that may be rolled back |
| **Non-repeatable read** | the same row read twice gives different values |
| **Phantom read** | the same query twice returns a different set of rows |
| **Lost update** | two transactions read-modify-write; one overwrites the other |

### Isolation levels

| Level | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| `READ UNCOMMITTED` | ❌* | possible | possible |
| **`READ COMMITTED`** ← Postgres default | ❌ | possible | possible |
| `REPEATABLE READ` | ❌ | ❌ | ❌* |
| `SERIALIZABLE` | ❌ | ❌ | ❌ |

\* **Postgres never allows dirty reads at all** — `READ UNCOMMITTED` behaves as
`READ COMMITTED`. And its `REPEATABLE READ` is stronger than the standard
requires: it also prevents phantoms, because it uses a snapshot.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

`SERIALIZABLE` in Postgres uses **SSI** (serializable snapshot isolation): it
does not lock more, it *detects* dependency cycles and aborts one transaction
with a serialization failure. So your application must be prepared to **retry**:

```java
catch (SerializationFailureException e) { retryTheWholeTransaction(); }
```

### The lost-update trap, and its fixes

```sql
-- ❌ read-modify-write in the application
SELECT balance FROM account WHERE id = 1;   -- 100
-- another transaction also reads 100 and writes 150
UPDATE account SET balance = 150 WHERE id = 1;   -- one update is lost
```

```sql
-- ✅ 1. do the arithmetic in the database
UPDATE account SET balance = balance - 100 WHERE id = 1;

-- ✅ 2. pessimistic lock
SELECT balance FROM account WHERE id = 1 FOR UPDATE;

-- ✅ 3. optimistic lock with a version column
UPDATE account SET balance = ?, version = version + 1
 WHERE id = ? AND version = ?;      -- 0 rows updated means someone else won
```

## 7. Locking

### Row locks

```sql
SELECT * FROM batch WHERE id = ? FOR UPDATE;          -- exclusive; others wait
SELECT * FROM batch WHERE id = ? FOR UPDATE NOWAIT;   -- fail immediately instead
SELECT * FROM batch WHERE id = ? FOR UPDATE SKIP LOCKED;  -- skip locked rows
SELECT * FROM batch WHERE id = ? FOR SHARE;           -- others may read, not write
```

**`SKIP LOCKED` is the neat one.** It turns a table into a work queue: each
worker takes rows nobody else has, with no coordination:

```sql
UPDATE job SET status = 'RUNNING'
 WHERE id IN (
     SELECT id FROM job WHERE status = 'PENDING'
      ORDER BY created_at LIMIT 10
        FOR UPDATE SKIP LOCKED
 ) RETURNING *;
```

### Deadlocks

```
T1: UPDATE a; UPDATE b;
T2: UPDATE b; UPDATE a;     -- 💥
```

Postgres **detects** deadlocks and kills one transaction with error `40P01`.
Prevention is the same as in Java: **acquire locks in a consistent order**, keep
transactions short, and touch as few rows as possible.

### Advisory locks

```sql
SELECT pg_advisory_lock(12345);       -- application-defined, not tied to a row
SELECT pg_try_advisory_lock(12345);   -- non-blocking
```

Useful as a distributed mutex — "only one instance runs this nightly job".

### DDL takes an exclusive lock

```sql
ALTER TABLE big_table ADD COLUMN x TEXT;             -- fast: metadata only (PG 11+)
ALTER TABLE big_table ADD COLUMN x TEXT DEFAULT 'a'; -- also fast in PG 11+
ALTER TABLE big_table ALTER COLUMN y TYPE bigint;    -- ⚠️ rewrites the whole table

CREATE INDEX ON big_table (col);                     -- ⚠️ blocks WRITES
CREATE INDEX CONCURRENTLY ON big_table (col);        -- ✅ does not block
```

> **`CREATE INDEX CONCURRENTLY` is the production answer.** It takes longer and
> cannot run inside a transaction, and if it fails it leaves an invalid index
> to drop — but it does not stop your application writing for ten minutes.

## 8. Upsert and idempotency

### The check-then-act race

```java
// ❌ two concurrent requests both see "not exists" and both insert
if (!exists(batchId)) { insert(batchId); }
```

This failed **12 of 14 concurrent batches** in ReconPilot before it was fixed.
There is a window between the check and the act, and under concurrency the
window is where you live.

### The fix: one atomic statement

```sql
INSERT INTO ingestion_batch (id, tenant_id, content_hash, status)
VALUES (?, ?, ?, 'RECEIVED')
ON CONFLICT (tenant_id, content_hash) DO UPDATE
    SET status = ingestion_batch.status        -- no-op update, so RETURNING fires
RETURNING id, (xmax = 0) AS inserted;
```

Two details worth knowing:

- **`DO UPDATE` with a no-op, rather than `DO NOTHING`.** `DO NOTHING` returns
  **no row** on conflict, so `RETURNING` gives you nothing and you cannot tell
  what happened. A no-op update makes the row come back either way.
- **`xmax = 0`** distinguishes an insert from a conflict — a neat trick worth
  knowing.

`EXCLUDED` refers to the row you tried to insert:

```sql
ON CONFLICT (id) DO UPDATE SET count = target.count + EXCLUDED.count;
```

> **Interview question:** *"How do you make an API idempotent?"* — "Give the
> caller a natural or supplied idempotency key, put a unique constraint on it,
> and write with `INSERT ... ON CONFLICT ... RETURNING` so the insert and the
> duplicate check are one atomic statement. Checking first and then inserting
> leaves a race window that concurrency will find. We used a SHA-256 of the file
> content as the key, so re-uploading the same file is recognised rather than
> double counted."

## 9. CTEs

```sql
WITH recent AS (
    SELECT * FROM recon_break WHERE created_at > now() - interval '7 days'
),
by_type AS (
    SELECT break_type, count(*) AS n, sum(delta_paise) AS total
      FROM recent GROUP BY break_type
)
SELECT * FROM by_type WHERE n > 100;
```

CTEs make a long query readable by naming its steps.

### Data-modifying CTEs — genuinely powerful

```sql
WITH new_tenant AS (
    INSERT INTO tenant (id, name) VALUES (?, ?) RETURNING id
)
INSERT INTO app_user (id, tenant_id, email, password_hash, role)
SELECT ?, new_tenant.id, ?, ?, 'ADMIN' FROM new_tenant;
```

This is ReconPilot's registration. **A single statement is atomic by itself**,
so if the second insert violates the unique index on email, the tenant insert is
undone with it — no transaction manager required.

That fixed a real bug: two un-transacted inserts left an orphaned tenant on
every duplicate registration, and nothing reported it.

```sql
-- Archive and delete in one statement
WITH moved AS (
    DELETE FROM active_job WHERE finished_at < now() - interval '30 days'
    RETURNING *
)
INSERT INTO archived_job SELECT * FROM moved;
```

> **Optimisation-fence note:** before PostgreSQL 12, every CTE was materialised
> — an optimisation barrier. Since 12, a CTE used once is inlined by default;
> `WITH x AS MATERIALIZED (...)` forces the old behaviour. Knowing this version
> boundary is a nice detail.

### Recursive CTEs

```sql
WITH RECURSIVE subordinates AS (
    SELECT id, manager_id, name FROM employee WHERE id = 1   -- anchor
    UNION ALL
    SELECT e.id, e.manager_id, e.name                        -- recursive part
      FROM employee e JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates;
```

For trees and graphs: org charts, category hierarchies, bill of materials.

## 10. Window functions

The thing SQL beginners reach for a loop to do.

```sql
SELECT
    break_type,
    external_txn_id,
    delta_paise,
    SUM(delta_paise)  OVER (PARTITION BY break_type)               AS type_total,
    ROW_NUMBER()      OVER (PARTITION BY break_type
                            ORDER BY delta_paise DESC)             AS rank_in_type,
    delta_paise - LAG(delta_paise) OVER (ORDER BY created_at)      AS change,
    SUM(delta_paise)  OVER (ORDER BY created_at
                            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
                                                                   AS running_total
FROM recon_break;
```

**`GROUP BY` collapses rows. A window function keeps every row and adds a
computed column over a "window" of related rows.**

| Function | Gives |
|---|---|
| `ROW_NUMBER()` | 1,2,3,4 — no ties |
| `RANK()` | 1,2,2,4 — ties share, then a gap |
| `DENSE_RANK()` | 1,2,2,3 — ties share, no gap |
| `LAG` / `LEAD` | the previous / next row's value |
| `FIRST_VALUE` / `LAST_VALUE` | endpoints of the window |
| `NTILE(4)` | quartile buckets |

**The classic use — top N per group:**

```sql
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY break_type
                                 ORDER BY delta_paise DESC) AS rn
      FROM recon_break
) t WHERE rn <= 5;
```

You cannot filter on a window function in `WHERE` — it is computed *after*
`WHERE` — hence the subquery.

## 11. Pagination done right

```sql
-- ❌ OFFSET: the database reads and DISCARDS 100,000 rows to give you 20
SELECT * FROM recon_break ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

`OFFSET` gets linearly slower as you page deeper. It is also **unstable**: if a
row is inserted while the user pages, rows shift and they see a duplicate or
miss one.

```sql
-- ✅ KEYSET (cursor) pagination: constant time, stable
SELECT * FROM recon_break
 WHERE (created_at, id) < (?, ?)        -- the last row of the previous page
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
```

With an index on `(created_at DESC, id DESC)` this is an index seek regardless
of depth. The tuple comparison handles ties on `created_at` correctly — which is
why `id` is in there.

**The trade-off:** you cannot jump to "page 500". For an API, an infinite-scroll
UI, or any large dataset, that is fine and usually preferable.

> Mentioning keyset pagination unprompted is a strong signal. Almost everyone
> writes `OFFSET` and never thinks about it again.

## 12. Row-level security

**This is ReconPilot's most interesting database feature and a genuinely
uncommon thing for a two-year candidate to have used.**

### The problem

Multi-tenant SaaS: every query must be filtered by tenant. If it is done in
application code, **one forgotten `WHERE tenant_id = ?` leaks another
customer's data.** There is no way to prove you never forgot.

### The solution: put it in the database

```sql
ALTER TABLE recon_break ENABLE ROW LEVEL SECURITY;
ALTER TABLE recon_break FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON recon_break
    USING      (tenant_id = current_setting('app.tenant_id', true)::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

```sql
-- the application sets this on every connection
SET app.tenant_id = '3f14583f-...';
```

Now `SELECT * FROM recon_break` returns only that tenant's rows. Not because
the query said so — because the database will not return anything else.

### The three things that all must be true

ReconPilot shipped RLS that was **enabled and completely inert** (defect D1).
All three of these are required:

1. **`FORCE ROW LEVEL SECURITY`** — without it, the **table owner is exempt**.
   Policies apply to everyone else and silently not to the account your
   application probably uses.
2. **Connect as a non-superuser.** **Superusers bypass RLS entirely.** So
   ReconPilot has two roles: `reconpilot` (owner, for migrations) and
   `reconpilot_app` (least privilege, for the application).
3. **`WITH CHECK` as well as `USING`.** `USING` filters what you can *read*.
   Without `WITH CHECK`, a tenant can **insert a row belonging to someone
   else** — and then not be able to see it.

> **Interview gold:** *"We enabled row-level security and it did nothing. The
> policies existed, the tests passed, and any tenant could read any row —
> because we connected as the table owner, who is exempt unless you say FORCE,
> and we only had USING, so writes were unconstrained. It taught me that a
> security control nobody has watched refuse is a hypothesis, not a control. We
> now have a test that connects as the least-privileged role, sets one tenant,
> and asserts the other tenant's rows are invisible."*

### The connection-pool danger

`SET app.tenant_id` is **session state**, and a pooled connection is reused. If
it is not cleared, the next borrower inherits the previous tenant.

ReconPilot wraps the `DataSource` and sets the variable on **checkout** and
clears it on **close** — double defence, because the consequence is one customer
seeing another's data.

```sql
-- NULLIF handles the case where the variable was never set:
-- current_setting(..., true) returns '' rather than raising, and ''::uuid fails
current_setting('app.tenant_id', true)
NULLIF(current_setting('app.tenant_id', true), '')::uuid
```

## 13. Roles and privileges

```sql
CREATE ROLE reconpilot_app LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO reconpilot_app;
GRANT USAGE ON SCHEMA public TO reconpilot_app;
-- deliberately NOT granted: DDL, TRUNCATE, DELETE on the event log
```

**Least privilege is not paperwork.** The application role in this project
cannot alter a table, so a SQL injection that reaches `DROP TABLE` fails. And
because it is not the owner, RLS applies to it.

### Roles are cluster-wide — a backup trap

**`pg_dump` does not include roles.** They live at the cluster level, so a dump
restored onto a fresh server comes back with no `reconpilot_app`, and every
`GRANT` and every RLS policy naming it fails.

That dump restores perfectly on the original server — where the role already
exists — and fails on a new one, which is the only place a backup is ever
actually needed.

```bash
pg_dump   --format=custom --file=db.dump        # the database
pg_dumpall --globals-only  > globals.sql        # ← the roles. Do not forget this.
```

## 14. VACUUM and bloat

Because of MVCC, dead row versions accumulate. `VACUUM` reclaims them.

```sql
VACUUM;                    -- reclaim space for reuse, non-blocking
VACUUM ANALYZE;            -- and refresh planner statistics
VACUUM FULL;               -- ⚠️ rewrites the table; takes an ACCESS EXCLUSIVE lock
ANALYZE;                   -- statistics only
```

**Autovacuum runs by default** and handles most cases. It falls behind on very
high-churn tables, and the symptoms are a table far larger than its data and
queries getting slower for no obvious reason.

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
  FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
```

**Never run `VACUUM FULL` casually in production** — it takes an exclusive lock
for the whole rewrite, which means downtime. `pg_repack` does the same job
online.

### Transaction ID wraparound

Postgres transaction ids are 32-bit and wrap. Vacuum "freezes" old rows to
prevent it. If autovacuum is disabled or permanently behind, the database will
eventually **refuse writes** to protect itself. Rare, dramatic, and worth
knowing the name of.

## 15. Bulk loading

Measured on this project, ingesting 1,000,000 rows:

```java
jdbc.batchUpdate("INSERT INTO transaction_event (...) VALUES (?,?,?,?)",
        rows, 1000, (ps, row) -> { ... });
```

```properties
spring.datasource.url=jdbc:postgresql://host/db?reWriteBatchedInserts=true
```

**`reWriteBatchedInserts` collapses a JDBC batch into one multi-row `INSERT`
instead of N single-row statements.** Driver-level, no code change.

**Measured: 70.8s → 51.0s.** A 28% improvement from one URL parameter.

Other levers:

- **`COPY`** is dramatically faster than any `INSERT` for pure bulk load —
  `COPY table FROM STDIN` via `CopyManager` in JDBC.
- **Drop indexes, load, recreate.** Maintaining five indexes per row is most of
  the cost of a big load.
- **One transaction, not one per row.** Each commit is an fsync.

And the memory rule that matters more than any of them: **stream, do not
accumulate.** ReconPilot parses a 2 GB file in constant memory by reading lines
and flushing batches. Collecting rows into a `List` first would put a million
objects on the heap — the difference between an app that works and one that
dies at 251 MB of a 256 MB limit.

## 16. Schema design: event log and bi-temporality

### Store facts, derive answers

ReconPilot's `transaction_event` table is **append-only**. Nothing updates a
transaction; corrections arrive as new events. Projections — totals, category
state — are derived and can be rebuilt from the log.

**Why:** a regulator asks "why was this merchant charged this, in March?" A
mutable row cannot answer. A log of facts can.

### Two different times

```sql
occurred_at TIMESTAMPTZ NOT NULL,      -- when it happened in the world
recorded_at TIMESTAMPTZ NOT NULL DEFAULT now()   -- when we learned about it
```

This is **bi-temporal modelling**, and it is how you answer *"what did we
believe on 1 April?"* as distinct from *"what was actually true on 1 April?"*.
A settlement file that arrives late has an old `occurred_at` and a new
`recorded_at`, and both questions have different, legitimate answers.

Any system where someone can be asked to justify a past decision — finance,
insurance, healthcare, payroll — eventually needs this. Knowing the term is
worth a lot in a fintech interview.

### Normalisation, briefly

- **1NF** — atomic values, no repeating groups
- **2NF** — 1NF + no partial dependency on part of a composite key
- **3NF** — 2NF + no transitive dependency (non-key depending on non-key)

**In practice:** normalise until it hurts, denormalise until it works.
Deliberate denormalisation — a cached count, a duplicated name — is fine when
you can say *why*, and when something keeps it consistent.

## 17. The traps, collected

| # | Trap | The answer |
|---|---|---|
| 1 | `FLOAT`/`REAL` for money | `BIGINT` minor units or `NUMERIC` |
| 2 | `TIMESTAMP` without time zone | Use `TIMESTAMPTZ` |
| 3 | Postgres `money` type | Locale-dependent; avoid |
| 4 | `UNIQUE` allows many NULLs | Use a partial unique index |
| 5 | Function on an indexed column | Index the expression instead |
| 6 | `LIKE '%x'` | Leading wildcard cannot use a B-tree |
| 7 | Composite index, non-leftmost filter | Unusable; mind the column order |
| 8 | Indexing everything | ~40% storage overhead and slower writes |
| 9 | `OFFSET` for deep pages | Linear slowdown and unstable; use keyset |
| 10 | Check-then-insert | Race; use `ON CONFLICT ... RETURNING` |
| 11 | `ON CONFLICT DO NOTHING` + `RETURNING` | Returns no row; use a no-op `DO UPDATE` |
| 12 | RLS without `FORCE` | The owner is exempt — silently inert |
| 13 | RLS without `WITH CHECK` | Reads filtered, writes not |
| 14 | Connecting as superuser | Bypasses RLS entirely |
| 15 | Session variable in a pooled connection | Leaks to the next borrower |
| 16 | `pg_dump` without `pg_dumpall --globals-only` | Restores with no roles |
| 17 | Long-running / idle-in-transaction | Blocks vacuum database-wide |
| 18 | `VACUUM FULL` in production | Exclusive lock; use `pg_repack` |
| 19 | `CREATE INDEX` on a live table | Blocks writes; use `CONCURRENTLY` |
| 20 | `EXPLAIN ANALYZE` on a DML statement | It actually runs it |
| 21 | `ALTER COLUMN TYPE` on a big table | Full rewrite under an exclusive lock |
| 22 | `ON DELETE CASCADE` everywhere | One delete can remove millions of rows |
| 23 | `count(*)` assumed free | MVCC means it must scan |
| 24 | Row-by-row inserts | Batch, and use `reWriteBatchedInserts` |
| 25 | `SELECT *` in production code | Breaks on schema change; fetches unused data |
